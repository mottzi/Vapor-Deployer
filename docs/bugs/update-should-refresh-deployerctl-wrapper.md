# Update Should Refresh The Deployerctl Wrapper

Status: fixed.

## Resolution

`deployer update` now invokes the newly activated deployer binary's `refresh-deployerctl` command after the deployer service restarts successfully and before the update summary is written. Root CLI updates refresh `/usr/local/sbin/deployerctl`, `/etc/deployer/deployerctl.conf`, and the panel-update helper directly. New setup/root refreshes also install a narrow sudoers-backed helper so future panel-triggered updates running as the service user can refresh only the deployerctl wrapper/config.

Existing installations that predate the helper need one root bootstrap after receiving this code:

```sh
sudo /home/vapor/deployer/deployer refresh-deployerctl
```

After that, panel updates can refresh wrapper-only changes without rerunning full setup.

## Summary

`deployer update` previously updated the installed Deployer executable and release/source assets, but did not refresh the root-owned `deployerctl` wrapper installed at `/usr/local/sbin/deployerctl`.

This meant changes to `DeployerctlTemplate.wrapperScript()` did not reach existing hosts through the normal panel Update flow. The only way to apply wrapper changes was to rerun `deployerctl setup`, which is much broader than a self-update and re-executed host provisioning steps that are unrelated to refreshing the operator wrapper.

This was a product/update bug. The panel Update button should be enough to make an existing installation run the latest control-plane code and the latest generated operator wrapper.

## Incident

While reviewing a proposed change to `Sources/Deployer/Commands/Setup/Templates/DeployerctlTemplate.swift`, specifically the `deployerctl help` output, we checked whether pushing that change to the configured Deployer branch and clicking Update in the VPS panel would update the live `deployerctl`.

The live host `root@mottzi.codes` confirmed the issue:

- `/etc/deployer/deployerctl.conf` has `BUILD_FROM_SOURCE='true'`.
- `/home/vapor/deployer/deployer.json` has `"buildFromSource" : true` and `"deployerBranch" : "dev"`.
- `/home/vapor/deployer` is a source checkout on branch `dev`.
- `/usr/local/sbin/deployerctl` is a generated root-owned shell script.
- The wrapper header says: `Auto-generated by deployer setup. Do not edit by hand; rerun deployer setup to update.`

The source update path correctly fetches and builds the latest Deployer binary from the configured branch. However, it never rewrites `/usr/local/sbin/deployerctl`, so wrapper-only changes remain stale after update.

## Root Cause

`DeployerctlStep` is only part of the setup pipeline.

During setup, `DeployerctlStep` writes both:

- `/etc/deployer/deployerctl.conf`
- `/usr/local/sbin/deployerctl`

The update pipeline does not run that step or any equivalent wrapper-refresh step.

For source installs, `UpdateCommand` runs:

- `SourceUpdateStep`
- `StopServiceStep`
- `ActivateReleaseStep`
- `StartServiceStep`
- `UpdateSummaryStep`

For release installs, it runs:

- `DownloadStep`
- `StageBinaryStep`
- `StopServiceStep`
- `ActivateReleaseStep`
- `StartServiceStep`
- `UpdateSummaryStep`

Neither path regenerates the operator wrapper. `SourceUpdateStep` only fetches/reset source, builds the binary, stages it, and records the new source revision. `StageBinaryStep` only stages the downloaded release binary and backs up assets. `ActivateReleaseStep` swaps the Deployer executable and assets, but not the root-level wrapper.

The mismatch is subtle because `deployerctl update` itself delegates to the installed Deployer binary. After the binary is updated, future Swift command behavior changes are live, but shell wrapper behavior remains frozen at the last setup run.

## Desired Behavior

`deployer update` should refresh the installed `deployerctl` wrapper as part of a successful update whenever the installation has enough metadata to do so safely.

At minimum:

- Source installs should regenerate `/usr/local/sbin/deployerctl` from the updated source code before the update is considered complete.
- Release installs should regenerate `/usr/local/sbin/deployerctl` from the newly installed release binary's embedded template logic.
- The generated config at `/etc/deployer/deployerctl.conf` should also be refreshed when template/config schema changes require it.
- Wrapper refresh should be rollback-aware, or at least avoid leaving the host with a wrapper generated by a failed candidate update.
- Manual rerun of full setup should not be required for ordinary wrapper/help/action changes.

## Design Notes

- The wrapper is installed as root and lives outside the service user's source checkout, so update code must account for permissions and ownership.
- The update process already starts from a root invocation in the normal `sudo deployerctl update` path. Panel-triggered updates spawn the installed binary directly, so verify that the detached child still has sufficient privileges in both `systemd` and `supervisor` modes.
- The update step should preserve the current separation between install-time config values and runtime configuration. It should not silently change operator choices that are intentionally fixed at setup time.
- The current wrapper config can be partially reconstructed from `/etc/deployer/deployerctl.conf`, `deployer.json`, and discovered executable ownership. If a full `SetupContext` is too setup-specific, introduce a smaller wrapper install context rather than forcing update to run setup steps.
- Avoid making `deployer update` depend on target-app health. This should be a control-plane maintenance action, not a workload validation gate.
- If regenerating `/etc/deployer/deployerctl.conf` is risky, split the fix into two phases:
  - Always refresh `/usr/local/sbin/deployerctl`.
  - Refresh `/etc/deployer/deployerctl.conf` only when all required values can be resolved and validated.
- The wrapper refresh should probably happen after the candidate binary/source has been staged but before the final summary. If it happens before service stop, a failed service restart could leave the wrapper ahead of the live binary. If it happens after successful service restart, the host may briefly run a new binary with an old wrapper, but rollback behavior is simpler.

## Possible Implementation

Introduce a dedicated update step, for example `RefreshDeployerctlStep`, and add it near the end of the update pipeline after `StartServiceStep` succeeds and before `UpdateSummaryStep`.

The step could:

1. Load existing deployerctl metadata from `/etc/deployer/deployerctl.conf`.
2. Load current `deployer.json`.
3. Resolve required paths and service metadata.
4. Write a freshly generated wrapper script to a staged temp path.
5. Atomically replace `/usr/local/sbin/deployerctl` with mode `0755`, owner `root:root`.
6. Optionally refresh `/etc/deployer/deployerctl.conf` via a staged write when all required values are known.

If wrapper config regeneration needs setup-only values that are not reliably stored today, this bug may require first extracting a persistent `DeployerctlInstallContext` or storing the missing fields explicitly during setup.

## Risks

- A wrapper generated by a newer binary may call actions that an older binary does not support if rollback happens after wrapper refresh.
- Regenerating config from incomplete metadata may erase important install-time values.
- Source installs and release installs may need slightly different timing because source installs build in place while release installs stage an extracted payload.
- `deployerctl` is an operator recovery tool, so a failed refresh must not corrupt or remove the existing working wrapper.

## Acceptance Criteria

- Changing `DeployerctlTemplate.wrapperScript()` and running panel Update updates `/usr/local/sbin/deployerctl` on an existing source install.
- The same class of wrapper change is applied through update on release installs.
- `sudo deployerctl help` reflects the updated wrapper after a successful update without rerunning setup.
- A failed update keeps the previous working `deployerctl` wrapper available.
- Wrapper file permissions remain executable and root-owned.
- Existing Swift command behavior updates still work as before.
- No full setup rerun is required for wrapper-only changes.
