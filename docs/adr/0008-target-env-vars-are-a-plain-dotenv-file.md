# Target-app environment variables are a plain `.env` file in the app working directory, not a deployer-managed store

The panel needs a way to manage environment variables for the deployed target app so operators stop SSHing in to edit unit files. The naive shape is "model env vars in the deployer's SQLite DB, render them out to the service manager on every change, expose CRUD endpoints." We picked the inverse: a single plaintext `.env` file at `\(paths.appDirectory)/.env` (e.g. `/home/vapor/apps/<appName>/.env`), owned `serviceUser:serviceUser` mode `0600`, that the *target app itself* reads at boot via Vapor's `DotEnvFile` — the deployer never reads the file back and the service manager never sees it. The settings page renders the file's current contents, accepts a full desired-state POST, and atomically rewrites the file (`.env.tmp` → `rename(2)`). That's the whole feature.

The reason is that the file is already the runtime artifact the consumer reads — Vapor's `DotEnvFile.load()` runs at boot against the process working directory, which is set to `paths.appDirectory` by both `SystemdTemplate.appUnit` and `SupervisorTemplate.appProgram`. Modelling env vars in the deployer's DB adds a second source of truth that the deployer would then have to render to the file anyway, plus a parser surface (DB-to-file), plus a schema/migration, plus glue between the two — all to recover behaviour the filesystem already provides. The single-admin VPS deployment model that this project targets does not need the audit-history / concurrent-edit / encryption-at-rest properties that a DB-backed store would unlock.

## Scope

- **v1 manages only target-app env vars.** The deployer's own secrets (`GITHUB_WEBHOOK_SECRET`, `PANEL_PASSWORD_HASH`) remain set by `SetupCommand` and baked into the unit/program file at provisioning time. Rotating the panel password through the panel it protects, or rotating the webhook secret without simultaneously updating GitHub's webhook config (which only `WebhookStep` does), are footguns this surface deliberately does not expose.

## Shape

- **Path:** `\(paths.appDirectory)/.env` — inside the per-app directory, which is already the process `WorkingDirectory`. The file is lazily created on first save by the deployer process (which already runs as `serviceUser`), so no setup-time step is required.
- **Activation:** Save writes the file and returns. The existing per-target Restart button applies the change. The save path does not restart on the user's behalf — a typoed `DATABASE_URL` would otherwise crash-loop the app and couple env editing to service control.
- **Edit model:** the form represents the full desired state of the file. One POST = one full-file render = one atomic write. There is no "save one row" at the protocol level because there is no "save one row" at the file level.
- **Validation:** keys match `^[A-Z_][A-Z0-9_]*$`; values are UTF-8, single-line, single-quoted on render with `'\''` escaping; size caps key ≤128 / value ≤4KB / file ≤64KB; `PATH`, `HOME`, `USER` are reserved (the service manager sets them).
- **Display:** values masked by default with per-row reveal, matching the deployer's existing pattern of "you're authenticated to the panel, but don't ambient-leak secrets on screen."
- **Route:** mounted under the existing `authRouter` in `Panel.usePanel`, so it inherits `PanelAuthenticator` for free — same protection level as `/`. No CSRF token, consistent with the existing login/logout forms relying on SameSite session cookies.

## Considered alternatives

- **Deployer SQLite DB as source of truth, render `.env` on each save.** Rejected. The properties this would unlock (per-row audit history, atomic multi-key transactions, "who changed what when") are not requested by the single-admin operator model. The cost is a migration, a new table, a render step, and a second place env-var state can drift to. The file already gives atomic multi-key writes via `rename(2)`. Audit-history can be added later as `.env.bak.<timestamp>` siblings without re-architecting.
- **Encrypted at rest.** Rejected. The deployer needs the key at startup to decrypt for rendering, so the key lives on the same host as the ciphertext — the bar against host compromise is not meaningfully raised, only the ceremony.
- **Bake env vars into the unit/program file** (extend `SystemdTemplate.appUnit` / `SupervisorTemplate.appProgram` with extra `Environment=` lines per saved var). Rejected because every save would then touch root-owned files in `/etc/supervisor/conf.d/` or the user-unit directory, require `daemon-reload` / `supervisorctl reread`, and re-introduce escaping problems specific to each service manager's config syntax. Decoupling env-var edits from the service-manager surface is the point.
- **Bridge `.env` into the service manager** via `EnvironmentFile=` (systemd) and a sourcing wrapper script (supervisor). Rejected as unnecessary: the target app reads `.env` itself via `DotEnvFile`, so neither service manager needs to know the file exists. Adding the bridge would be solving a problem that does not exist for Vapor apps and would create one for any non-Vapor target.

## Consequences

- **The feature assumes the target app reads `.env` from its working directory.** For Vapor apps this is automatic (`DotEnvFile`); a non-Vapor Swift target deployed via this deployer would need to do its own dotenv loading or the file is inert. Acceptable given the project name.
- **The file lives inside the target's git checkout** (`paths.appDirectory` is where `AppCheckoutStep` runs `git fetch/checkout/pull`). This is safe in practice because every Vapor app's `.gitignore` lists `.env` and no setup or deploy step runs `git clean -fdx`, but any future operation that does so would wipe operator-managed secrets. A future maintainer adding a cleanup step needs to know this.
- **Setup re-runs must never overwrite an existing `.env`.** This is currently enforced by *not having setup touch the file at all* — lazy creation by the deployer is the entire mechanism. Adding any setup-time `.env` handling later must preserve this invariant.
- **Atomic write is non-negotiable.** Half-written `.env` files survive into the next app boot and `DotEnvFile` will parse the truncation as best it can. The save handler writes to `\(appDirectory)/.env.tmp.<pid>` and `rename(2)`s into place; `Configuration.resolved()`-style validation (key regex, size caps, reserved keys) gates the write path so a malformed POST cannot produce a file that breaks the next boot.
- **Multi-target is a future-you problem.** `Configuration.target` is currently singular and the settings route is `/<panelRoute>/settings`. If the deployer ever manages multiple targets, the path scheme (`/home/vapor/apps/<appName>/.env`) already scales, but the route shape does not — it would need to become `/<panelRoute>/targets/<name>/settings`. Called out so it is not re-derived from scratch.
