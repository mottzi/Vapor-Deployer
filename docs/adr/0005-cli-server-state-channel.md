# CLI ↔ server state channel: flock for mutex, HTTP for query

The deployer can be self-updated from two paths — the panel's `UpdateAction` and a user-typed `deployer update` in a shell — and target-app deploys run in the server alongside both. The pre-v1 design used `flock(2)` on `.deployer-update.lock` as the only cross-process barrier and an in-memory `isUpdating` flag in the `Updater` actor for everything else, with a sentinel file (`.deployer-self-update.sentinel`) carrying "child has exited" back from the detached update child to its parent server (see [ADR 0001](0001-self-update-runs-in-detached-child.md)). Update-vs-update was hardened by the kernel; update-vs-deploy was explicitly best-effort because the CLI had no channel to ask the server "are you deploying right now?" and the server had no channel to learn "a CLI just started updating."

v1 closes that gap by introducing two cooperating mechanisms with different jobs:

- **`flock` remains the mutex** for update-vs-update. The kernel-enforced atomic acquire-or-fail is crash-safe (auto-released on process exit, including SIGKILL/OOM) and works when the server is down — a primary property because `deployer update` is itself a recovery path.
- **A localhost HTTP query endpoint** (`GET /control/state`, Bearer-token, returns `{ "phase": "ready" | "deploying" | "updating" }`) lets the CLI ask the running server its current `DeployerPhase` before doing anything. This is a **query, not a claim**: there is no server-side lease, no release protocol, no TOCTOU mutex pretense. The lockfile is still the only mutex. The route is namespaced `/control` (control plane, not user/admin UI) — it has no human-facing surface, just a machine-to-machine state query the CLI uses to steer itself.

The state itself becomes **lockfile-derived rather than in-memory-authoritative**. A long-lived polling Task on the `Updater` actor calls `flock(LOCK_EX | LOCK_NB)` on the lockfile every 2 s as a non-destructive peek (success → release immediately, lock was free; `EWOULDBLOCK` → lock is held by someone else) and updates `DeployerPhase` accordingly. The panel therefore reflects updates regardless of which path launched them — the asymmetry between "panel-launched updates are visible, CLI-launched updates are invisible" disappears. The sentinel file is retired in the same move: its only state-machine job was telling the parent "the child has exited so clear `isUpdating`," and lockfile release already signals that, more robustly and on every exit mode (the sentinel never fired on SIGKILL/OOM; the kernel always releases `flock`). Its error-message payload was written but never read.

To prevent flicker between `Updater.startUpdate` returning and the spawned child actually acquiring the lock, the in-memory flag stays as a **sticky bit** ORed into the derived `isUpdating`: set when the panel spawns a child, cleared by the polling Task once it has observed the lock taken at least once and then released. A 5 s timeout clears the sticky bit if the lock is never observed taken (the child died before acquiring). CLI-launched updates need no sticky bit — `UpdateLock.acquire` runs early enough in the pipeline that the next 2 s poll tick reliably catches it.

All server-side publishers of `DeployerPhase` must use the same resolver semantics: the update lock and updater sticky bit win over deploy state, then the operation lock and queue state decide `deploying`, and only the absence of both yields `ready`. This is intentionally centralized because multiple runtime tasks can publish the badge: the updater poller, panel SSR/resubscribe rendering, queue completion, control-state reporting, and the operation-event bridge. A publisher that checks only the lock files and ignores the sticky bit can incorrectly emit `ready` during the panel-spawn-to-lock-acquire window, causing visible `ready → updating → ready` cycles even though only one update was launched.

To close the gap symmetrically, `Queue.start` also performs the same non-destructive `flock` peek before flipping `isDeploying = true`: if the update lock is held, the deploy refuses with `.queueBusy`. The CLI side of the symmetry is the `/control/state` check before `UpdateLock.acquire`: if `phase != "ready"`, refuse with a phase-named message. The CLI treats **connection refused** (server not running) as proceed — this is the deliberate carve-out that preserves the "self-update works when the server is broken" property. 401/403/404/5xx all refuse, because they indicate the server exists but cannot establish that it is in a known-ready state.

The control token is provisioned by the server at boot: read from `<installDir>/.deployer-control.token` (mode `0600`, owned by service user) if present; otherwise generated as 32 hex-encoded bytes from `SystemRandomNumberGenerator` and written. This self-heals on upgrade from older installs without a migration script and survives accidental deletion. If the token cannot be read or written, the control route is not mounted; the panel and pushevent paths still serve, and CLI calls see 404 → refuse. (The token is also a co-tenancy check, not a permission check: any process able to read `0600` files owned by the service user is, by definition, on the same host as the same user — exactly the trust boundary this channel cares about.)

Rejected alternatives:

- **Replace `flock` with a server-mediated claim API** (`POST /control/update/claim` returning a lease the CLI releases). Loses the kernel-enforced atomicity for free, requires lease/heartbeat/TTL plumbing to handle CLI crashes (which `flock` handles via `close(2)`-on-exit), and — fatally — makes `deployer update` depend on a healthy server, removing it as a recovery primitive.
- **Bind the control endpoint on a dedicated Unix domain socket** instead of the existing TCP listener. Cleaner in principle (no token needed, filesystem perms as access control, no possibility of accidental public exposure). Rejected because Vapor's HTTP server is not ergonomically configured to bind two endpoints in one `Application`, Foundation's `URLSession` cannot dial a UDS so the CLI would need NIO-level client code, and the existing TCP listener is already kernel-bound to `127.0.0.1` and not proxied by the deployer-managed nginx config — the network surface is already constrained. The token shifts the access boundary from filesystem perms to "the same filesystem perms gate the token file," which is the same boundary by a different name, for substantially less code.
- **CLI pushes state to the server over HTTP** (`POST /control/update/begin` / `/end`) instead of the server polling the lockfile. Re-introduces the "server must be up" dependency the lockfile carefully avoids, requires server-side TTL/heartbeat for CLI-crash detection, and would need lockfile-polling anyway as a fallback for the server-was-down case — strictly additive complexity for sub-second latency the panel does not need.
- **Filesystem watch on the lockfile** instead of polling. `flock` state transitions are advisory and produce no filesystem events; `inotify`/`kqueue` on the file would see opens and closes from any process touching it, not lock acquisitions. Not a viable primitive for this signal.

The cost accepted: one `flock`-peek syscall every 2 s for the lifetime of the server (negligible), one token file in the install directory, and a Bearer-token middleware on a single route. CONTEXT.md drops the "Mutual exclusion with `Queue.isDeploying` is best-effort" language; the comment on the `Updater` actor referencing this ADR replaces the comment referencing this best-effort gap.
